# Скрипт: улучшение результата Kaggle (анализ возможностей)

**Назначение:** пошаговый playbook для агента и разработчика после первой рабочей модели и первого public score.  
**Не цель:** сразу учить 10 новых моделей. Сначала **разложить ошибку**, потом одно изменение.  
**Эталон применения:** `transformers_goods` (MEPhI subject detection, LinearSVC, public 0.90084).  
**Копировать в:** `Разработка/` следующего репозитория (имя файла оставить).

---

## Когда запускать

Есть:

1. Воспроизводимый пайплайн (скрипт, не только ячейки).
2. Хотя бы один **принятый** Kaggle submission и public score.
3. Зафиксированные seed, сплит, пути к train/test/submission.

Нет смысла гонять этот скрипт до первого валидного CSV.

---

## Инварианты (не нарушать)

1. **Одна точка отсчёта.** Эталон: файл CSV, SHA256, public score, гиперпараметры, дата.
2. **Один валидационный протокол** для всех идей (тот же seed, тот же тип сплита).
3. Сравнивать модели по **той же метрике, что на Kaggle** (здесь: `f1_score(..., average="macro", zero_division=0)`).
4. Параллельно смотреть **micro / weighted F1** (или accuracy): если macro растёт, а public падает — вы лечите редкие классы, которых нет в public-доле теста.
5. Не выбирать финал только по public при лимите сабмитов. Public ≈ часть теста (часто ~30%).
6. Одно содержательное изменение → один прогон → решение «оставить / откатить».
7. Эталонный сабмит не затирают; новые кладут в `submissions/<experiment>/`.

---

## Шаг 0. Зафиксировать эталон

Записать в `submissions/<name>/meta.json` или в ревью:

| Поле | Пример |
|------|--------|
| Путь CSV | `submissions/linear_v2/submission.csv` |
| SHA256 | из `meta.json` |
| Public score | 0.90084 |
| Модель | LinearSVC, unique_text, TF-IDF word 1–2 + char 2–6, C=3 |
| Сплит | StratifiedGroupKFold / GroupKFold по ключу без утечки |
| Метрика Kaggle | F1-macro |

Если строки группируются (один текст / пациент / сигнал — много строк) — **группа не должна попадать и в train, и в val**.

---

## Шаг 1. Per-class разложение ошибки

На **OOF или одном group-holdout** эталонной модели:

1. Таблица: `subject` (или класс), support, precision, recall, F1.
2. Сортировка по F1 ↑ и отдельно по support ↓.
3. Три корзины:
   - **частые + низкий F1** — почти весь public;
   - **средние**;
   - **1–3 примера, F1=0** — бьют CV, на public могут не влиять.

**Решение:** если просадка в частых — копать confusion. Если только singleton — линейкой / «ещё C» топ не взять.

---

## Шаг 2. Confusion-пары + сырые примеры

1. Top-N пар `(true, pred)` по числу ошибок.
2. Отдельно пары с большим вкладом в **macro** (редкий класс).
3. По 10–20 **сырых** объектов (`text`, сигнал, таблица) на пару.

Искать: синонимы, опечатки, слишком короткий ввод, один шаблон — разные метки.

**Возможности:** нормализация, словари **только из train**, точечные правила на 5–10 пар (проверять на holdout, легко подогнать public).

---

## Шаг 3. Срезы (не только классы)

Считать качество на срезах holdout:

| Срез | Зачем |
|------|--------|
| Длина / размер объекта | короткий ввод = потолок простых признаков |
| Редкость класса (1 / 2–5 / >50) | политика rare vs frequent |
| Дубликаты vs уникальные ключи | перекос частоты (в этом проекте unique_text лучше all-rows) |
| Спецсимволы, цифры, язык | мусор в токенах |
| Уверенность модели | см. шаг 4 |

Где провал **сконцентрирован** — туда фичи, а не «увеличить max_features всем».

---

## Шаг 4. Уверенность vs ошибка

Для линейных: `decision_function` / разница top-1 и top-2. Для вероятностных: max proba.

| Паттерн | Что пробовать |
|---------|----------------|
| Низкая уверенность, частый класс | ансамбль, encoder только на «серых» |
| Высокая уверенность, неверный класс | классы неразделимы текущими признаками |
| Редкие всегда неуверены | мягкие веса (sqrt inverse), не жёсткий 1/n |

---

## Шаг 5. Данные: утечки и коллизии

- Пересечение train/test по **сырому** ключу и по **нормализованному**.
- Конфликт меток у одного ключа в train.
- Дубликаты: учиться на всех строках или на уникальных (сравнить на **том же** сплите).

Нормализация, которая склеивает разные объекты, — отдельный риск (в этом проекте 5 пар train/test после `ё→е` / lower).

---

## Шаг 6. Абляции эталона

По одному выключению, тот же сплит:

- без char n-grams / без word;
- unique vs all rows;
- class_weight on/off;
- C / lr вокруг текущего значения.

Если выкинуть компонент — метрика падает сильно, его нельзя выкинуть в следующей модели (например encoder не должен резать короткие строки).

---

## Шаг 7. Диагноз потолка (обязательный вывод)

Зафиксировать **одну** букву:

| Код | Смысл | Типичное действие |
|-----|--------|-------------------|
| **A** | Путаются близкие классы, мало сигнала в объекте | encoder / более богатые признаки (часто GPU) |
| **B** | Macro тянут редкие, public уже ок | GPU может не поднять public; смотреть private/курс |
| **C** | Систематические паттерны в сырых полях | дешёвые фичи и правила |
| **D** | Линейка уже выжала запас (малый % отличий дал скачок LB) | не сетка из 20 SVC; смена семейства моделей |

Пример: LogReg 0.87394 → LinearSVC 0.90084 при ~6% других меток = **D** для дальнейших линейных сеток; до топа (~0.92) скорее **A**.

---

## Шаг 8. Что пробовать после диагноза

Порядок, не параллельно всё сразу:

1. Починить частые confusion-пары (нормализация, точечные фичи).
2. Если **A**: более ёмкая модель; early stopping по **метрике Kaggle**; веса классов мягкие; тот же anti-leak сплит.
3. Смесь эталона и новой модели по **holdout**, не по public.
4. 1–2 сабмита на идею; эталон оставить среди final (лимит 2 final на Kaggle).

Запрещено правилами конкретного соревнования — не делать (внешняя разметка теста, LLM без модели на train, prod-веса и т.д.).

---

## Шаг 9. Как не обмануть себя

- Не оптимизировать только CV-macro, если цель — текущий public (и наоборот).
- Правило «если X → класс Y» проверять: не упал ли F1 соседних классов.
- Не затирать эталонный CSV.
- Не сдавать прогон, у которого holdout катастрофически ниже эталона (пример: encoder_v1, F1 ~0.006).
